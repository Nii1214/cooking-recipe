## 1. 概要

### 1.1 何を作ったか

**メールアドレス登録なしで、アプリを試せる「ゲストログイン」** を追加した。

- ログイン画面（`/login`）と LP（`/`）に **「ゲストで試す」** ボタンを置く
- 押下すると Supabase の **Anonymous Sign-In** でセッションを確立する
- 以降は通常ログインと同様に `/top` やレシピ作成などが使える（プロフィール未作成なら `/profile/new` へ）

### 1.2 何を作っていないか（スコープ外）

| 項目 | 状態 |
|------|------|
| 本登録（Identity Linking） | 未実装 |
| 日次バッチ（匿名ユーザー削除） | 未実装（方針のみ決定） |
| ゲスト専用 RLS 関門（`is_anonymous` チェック） | 第 1 段階では追加しない |

## 2. 背景と目的

### 2.1 背景

本番デモ（[https://cooking-recipe-liard.vercel.app/](https://cooking-recipe-liard.vercel.app/)）公開後、次の課題があった。

- 新規登録 → メール確認 → ログイン … のハードルが高い
- デモやポートフォリオ閲覧者が **中身をすぐ試せない**

### 2.2 目的

| 目的 | 内容 |
|------|------|
| **体験** | ワンクリックでアプリ内に入れる |
| **セキュリティ** | ゲスト同士・本ユーザーとのデータ混線を防ぐ |
| **保守** | 既存の Auth / RLS / クリーンアーキテクチャを大きく崩さない |
| **データ寿命** | ゲストデータは一定期間後に削除する（バッチは後続 PR） |

---

## 3. 採用方針（案 A）

3 案の比較は ADR 007 を参照。**Supabase Anonymous Sign-In** を採用した。

```
┌─────────────┐     signInAnonymously()     ┌──────────────────┐
│  ブラウザ    │ ──────────────────────────► │ Supabase Auth    │
│  /login     │ ◄────────────────────────── │ auth.users       │
└─────────────┘     セッション Cookie        │ is_anonymous=true│
       │                                      └──────────────────┘
       ▼
┌─────────────┐     auth.uid() で RLS        ┌──────────────────┐
│  /top 等    │ ──────────────────────────► │ PostgreSQL       │
└─────────────┘                              │ profiles, recipes│
                                             └──────────────────┘
```

**ポイント**

- ゲストも **正規の Supabase セッション** を持つ（Cookie だけの擬似ログインではない）
- ゲストごとに **独立した `auth.uid()`** が付与される
- 既存 RLS（`author_id = auth.uid()` 等）がそのまま効く

## 4. ユーザー体験フロー

### 4.1 ゲストログイン成功時

```
/login
  └─ 「ゲストで試す」クリック
       └─ guestLoginAction（Server Action）
            └─ signInAnonymously()
                 └─ redirect /top
                      ├─ プロフィールなし → /profile/new
                      └─ プロフィールあり → レシピ一覧表示
```

### 4.2 通常ログインとの違い

| 項目 | 通常ログイン | ゲストログイン |
|------|-------------|---------------|
| 入力 | メール + パスワード | なし（ボタン 1 つ） |
| Auth API | `signInWithPassword` | `signInAnonymously` |
| メール | 必須 | なし |
| ログイン後の画面 | `/top` | `/top`（同じ） |
| データ操作 | 自由 | **第 1 段階では同様に自由** |

### 4.3 画面（ログイン）

- 既存のメール/パスワードフォームの **下** に区切り線 + 「ゲストで試す」
- ボタンは **Secondary**（枠線・白背景・emerald 系テキスト）
- 注記: 「アカウント不要で体験できます（データは一定期間後に削除されます）」

## 5. 権限とデータの考え方

### 5.1 ゲストに許可すること（第 1 段階）

**本登録ユーザーと同様** に、自分の uid スコープ内で操作可能とする。

- プロフィール作成
- 家族グループ作成
- レシピ CRUD
- お気に入り

理由: 既存 RLS が `auth.uid()` ベースのため、**追加ポリシーなしでもゲスト同士のデータは分離**される（ADR 007 Q&A 参照）。

### 5.2 ゲストに制限しない理由

- 体験として「ちゃんと使ってみる」ことを優先
- `is_anonymous` を全テーブルに書く保守コストを避ける
- 悪用・スパムは **Auth レート制限 + 日次削除** で対処

### 5.3 将来追加しうる制限

本登録を促したい操作だけ、RLS ヘルパー `is_permanent_user()` 等で関門を設ける（別 PR）。

## 6. データ削除（日次バッチ）— 方針のみ

第 1 PR では **未実装**。採用方針は次のとおり。

| 項目 | 内容 |
|------|------|
| **対象** | `auth.users.is_anonymous = true` かつ作成から 24 時間超（例） |
| **手段** | Supabase Auth Admin API または DB 関数 + Cron |
| **連鎖削除** | `auth.users` 削除 → 関連テーブル CASCADE |
| **本登録済み** | Identity Linking 後は `is_anonymous = false` → **対象外** |

### 6.1 マイグレーション（バッチ前提）

`families.owner_id` に **`ON DELETE CASCADE`** を付与済み。

- 以前: オーナー削除時に FK エラーでバッチが失敗しうる
- 以後: ユーザー削除 → オーナーだった家族 → `family_members` も連鎖削除

| テーブル | ユーザー削除時 |
|---------|---------------|
| `profiles` | CASCADE |
| `recipes`（author） | CASCADE |
| `recipe_favorites` | CASCADE |
| `family_members`（user_id） | CASCADE |
| `families`（owner_id） | CASCADE（今回追加） |

※ S3 サムネイルの孤立ファイル削除は別途検討。

## 7. アーキテクチャ

### 7.1 層ごとの責務

```
presentation          app                    usecase              infrastructure
─────────────────────────────────────────────────────────────────────────────────
GuestLoginForm   →   guestLoginAction   →   GuestLoginUseCase  →  AuthRepositoryImpl
  （ボタン）            （Server Action）      （オーケストレーション）   signInAnonymously()
                                                                              ↓
                                                                         Supabase Auth API
```

| 層 | ファイル | 責務 |
|----|---------|------|
| **presentation** | `guest-login-form.tsx` | ボタン表示、pending / エラー表示 |
| **app** | `guest-login.action.ts` | UseCase 呼び出し、成功時 `/top` へ redirect、エラー日本語化 |
| **usecase** | `guest-login.usecase.ts` | `signInAnonymously()` を実行し Result を返す |
| **infrastructure** | `auth-repository-impl.ts` | `supabase.auth.signInAnonymously()` |
| **domain** | `auth-repository.ts` | `signInAnonymously()` インターフェース |

### 7.2 DI の組み立て（現状）

認証系（login / signup / guest-login）は **`DIContainer`** 経由で UseCase を取得する。

```typescript
const useCase = DIContainer.getGuestLoginUseCase();
await useCase.execute();
```

家族・プロフィール等は **action 内で deps を直渡し** する新しいパターン。認証だけレガシー方式のため、ゲストログインも **既存 auth に合わせた**。統一リファクタは **別 PR** 推奨。

### 7.3 保護ルート

`proxy.ts` は変更なし。ゲストも **セッションあり = 認証済み** として保護ルートにアクセスできる。

## 9. Supabase / 本番設定

### 9.1 ローカル

```bash
# config.toml で enable_anonymous_sign_ins = true 済み
# 反映には再起動が必要（起動中のまま変更しても Anonymous は OFF のまま）
npx supabase stop && npx supabase start
npx supabase db push   # または --local
```

### 9.2 本番（Supabase Cloud）

| 設定 | 場所 | 値 |
|------|------|-----|
| Anonymous Sign-Ins | Authentication → Providers | **Enable** |
| マイグレーション | CLI | `npx supabase db push` |
| レート制限 | Auth 設定 | `anonymous_users`（IP あたり）を適宜 |

### 9.3 失敗時に見るエラー

| 画面メッセージ | 原因の例 |
|---------------|---------|
| ゲストログインは現在利用できません | Dashboard で Anonymous が OFF、またはローカル Supabase を再起動していない |
| ゲストログインに失敗しました | `data.user` が null、通信エラー |
| （汎用）エラーが発生しました | 環境変数未設定、API キー不正 |

## 11. つまずきやすい点

| 症状 | 確認すること |
|------|-------------|
| ボタン押下でエラー | Supabase で Anonymous Sign-In が有効か |
| ログインできたがすぐ落ちる | Vercel の `NEXT_PUBLIC_SUPABASE_*`、Redeploy |
| ゲストなのに他人のデータが見える | **起きない想定**。RLS + 独立 uid。起きたら重大バグ |
| バッチでユーザー削除できない | `families.owner_id` CASCADE マイグレーション未適用 |
| DIContainer だけ古いパターン | 意図的。auth 全体のリファクタは別 PR |
