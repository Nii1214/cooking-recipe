# ADR 008: レシピ画像の保存先

## 背景

レシピのサムネイルは当初 **AWS S3（非公開バケット + プレサイン URL）** に保存していた。

個人開発の運用では、次のコストが積み上がっていた。

- AWS アカウント・IAM ユーザー・アクセスキーの管理
- S3 バケットの公開設定・バケットポリシーの保守
- Vercel に `AWS_*` 環境変数を 4 つ置く二重のインフラ
- Auth / DB は Supabase、画像だけ AWS という分割

一方、Supabase Pro プランでは Storage に **100GB** が含まれており、家族向けレシピ帳の画像量であれば十分である。

あわせて、元画像をそのまま保存すると容量を圧迫するため、**保存前のリサイズ**もこの変更に含める。

---

## 目的

| 項目 | 内容 |
|------|------|
| **運用** | 画像保存を Supabase に寄せ、AWS の永続化をやめる |
| **容量** | 保存前に縮小し、形式を WebP に揃える |
| **セキュリティ** | URL を知っているだけで誰でも見られる状態にはしない |
| **実装** | 既存の domain 契約 / usecase / Server Action の形を崩さない |

---

## 評価基準（優先順位）

1. **運用コスト** … アカウント数、環境変数、障害時の調査先
2. **セキュリティ** … 家族外への漏洩、期限切れ URL
3. **容量** … 保存サイズとプラン枠
4. **実装難易度** … 既存アーキテクチャとの親和性

---

## 案 A: Supabase Storage（非公開 + 署名 URL）+ サーバー側 sharp

### 概要

`recipe-images` バケットを非公開にする。アップロードは Server Action → usecase → sharp → `storage.upload()`。表示は `createSignedUrl`（1 時間）。閲覧範囲は `recipes` と同じ RLS（本人 + `is_same_family()`）。

### メリット

| 観点 | 内容 |
|------|------|
| **運用** | AWS アカウントと `AWS_*` 環境変数が不要。Auth / DB / Storage が同じプロジェクト |
| **容量** | Pro の 100GB 枠。保存前リサイズで実使用量を抑える |
| **セキュリティ** | 非公開 + 期限付き URL。署名発行時に RLS が効く |
| **実装** | 既存の deps パターンに `imageProcessor` を足すだけで済む |

### デメリット

| 観点 | 内容 |
|------|------|
| **セキュリティ** | S3 時代はサーバーの IAM で署名していたため RLS が不要だった。Storage では SELECT ポリシーを正しく書かないと家族画像が見えない / 他人に見える |
| **実装** | sharp 依存の追加。Vercel では native バイナリの扱いが必要 |
| **移行** | 既存 S3 オブジェクトはパス形式が違うため移行せず NULL 化する |

---

## 案 B: AWS S3 を維持し、リサイズだけ追加する

### 概要

保存先は S3 のまま、usecase に sharp を足して容量だけ抑える。

### メリット

- 既存のプレサイン実装をそのまま使える
- Storage RLS を設計し直さなくてよい

### デメリット

- **運用コストが下がらない**（今回の主目的を満たさない）
- AWS と Supabase の二重管理が残る
- Pro の 100GB を使わない

---

## 案 C: 公開バケット + 公開 URL

### 概要

`recipe-images` を `public = true` のままにし、`getPublicUrl` で表示する。署名 URL は不要。

### メリット

- 実装が最も単純。CDN キャッシュも効きやすい

### デメリット

- URL を知っていれば誰でも見られる（家族の写真を想定する要件に反する）
- 現行 S3 非公開の姿勢から後退する

## 採用しない設計

### Supabase Image Transformation（配信時変換）のみ

Pro プランの Image Transformation は**配信時**にサイズを変える。元ファイルはフルサイズのまま残るため、**保存容量の削減にはならない**。今回の目的（容量圧迫の回避）には使わない。

### クライアント側 canvas のみのリサイズ

送信量は減るが、クライアントを信頼できない。サーバー側で再変換するなら二重になる。検証と変換はサーバーに寄せる。

---

## 決定内容

**案 A を採用する。**

| 項目 | 方針 |
|------|------|
| **保存先** | Supabase Storage バケット `recipe-images`（非公開） |
| **AWS** | S3 実装・SDK・環境変数を削除する。既存オブジェクトは移行しない |
| **パス** | `{authorId}/{uuid}.webp`（INSERT RLS の `{userId}/` プレフィックスと一致させる） |
| **変換** | サーバー側 sharp。EXIF 回転、長辺 1200px、WebP quality 80 |
| **表示** | `createSignedUrl`（1 時間）。失敗時は `undefined`（ページ全体は落とさない） |
| **閲覧 RLS** | 本人、または `is_same_family(フォルダ名の uuid)` |
| **既存データ** | `recipes.thumbnail_url` を NULL 化する |

変更理由の要約:

1. **運用コストが高い**ため、画像も Supabase に寄せる
2. **Pro プラン時は Storage 100GB** があり、家族向け用途では足りる
